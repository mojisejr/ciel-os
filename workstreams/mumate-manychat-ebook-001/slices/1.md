# Slice 1 — โครงแอปและทางทดสอบบน staging

## Scope

**repo ของแอป**
- สร้าง repo ส่วนตัวตามชื่อที่เจ้าของอนุมัติ แล้วลงทะเบียนเป็น project ใน ciel-os
- มี `container-build` ที่สร้าง image tag = git SHA

**ตัวแอป**
- มี `/api/health`
- มี endpoint หนึ่งตัวที่รับ External Request จาก ManyChat ตอบภายใน 1 วินาทีเสมอ แล้วค่อยทำงานต่อ
- ตรวจ secret ของ request ที่มาจาก ManyChat
- ด่านกันพลาด: บน staging แอปเรียก ManyChat API ได้เฉพาะ subscriber ใน allowlist ของทีม

**mumate-infra**
- เพิ่ม service ตัวที่สาม, Caddy route ของ staging และ `env/*.example`
- ให้ `release`, `staging-follow`, `promote-production` และ `rollback` รู้จักแอปนี้ ยังไม่เปิดบน production
- เพิ่ม `bin/ebook.sh status`: ใช้อ่านอย่างเดียว และมี `--dry-run`

**ฐานข้อมูล**
- ตารางแรกบน `pgstaging` เก็บ event ของแต่ละ request
- migration เป็นแบบเพิ่มอย่างเดียว รันซ้ำได้

**ManyChat**
- Duplicate flow จริงเป็น `Bazi E-Book 95 [TEST]` เปิดด้วย keyword ทดสอบที่ไม่มีคำใดคำหนึ่งของ flow จริง
- ใช้ tag และ field ใหม่ที่ขึ้นต้นด้วย `bot_` เท่านั้น
- External Request ชี้ไป staging และตอบกลับด้วย `sendContent`

## Acceptance

- merge แล้ว staging deploy แอปเองภายใน 3 นาที, `bin/ops-status.sh` ✅ และ Discord ประกาศ

  → `bin/ebook.sh status` บน staging เห็นแถวนั้น
- subscriber ที่ไม่อยู่ใน allowlist ถูกกัน ไม่ได้รับข้อความ และมีบันทึกว่าถูกกัน
- flow จริง "Bazi E-Book 95" รวมถึง trigger, tag และ field เดิม ไม่เปลี่ยน
  ตรวจโดยเทียบกับ export วันที่ 2026-11-08 แล้วต่างกันแค่ตัวเลขสถิติ
