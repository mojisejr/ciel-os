# 1. prod-sql.sh

1. **`bin/prod-sql.sh`** runs on a MuMate host against that host's
   application database and takes a SQL file on stdin or as a path.
   - Reads the URL from `env/bazi.env` itself, strips shell quotes
     silently, and passes it to psql through the environment.
   - Prints only `name|value` result lines, where a SQL statement makes
     such a line with `SELECT 'name|' || …`; drops every other line; on
     failure prints one fixed line with the exit code and nothing else.
   - Runs in one transaction. `--dry-run` rolls back at the end and is the
     default. `--commit` commits. `--expect N` is optional: when given, the
     tool rolls back unless the statement reports `changed|N`.
   - `--help` says what it does, what it never prints, and when to stop and
     ask (the `OWNER.md` sense of serious).
2. **Test** `scripts/prod-sql.test.sh` plants a canary password in a fake
   quoted env file and a stub psql that echoes its connection string on
   error. The canary must never appear: on success, on a connection error,
   on a SQL error, on an `--expect` mismatch, or with an empty or malformed
   URL. The test joins `scripts/test-all.sh`.
3. **Runbook 01**, agent section: production database work goes through
   `bin/prod-sql.sh`, never a one-off command. Reads of counts or totals
   (no member content) need no question. Writes are done and reported. The
   agent asks first only for something serious.
4. **Proof on production:** one read through the tool on prod-1, counting
   `ai_question_log` rows. Its output shows only the declared lines.

## Acceptance

- `scripts/prod-sql.test.sh` passes, and fails when the filter is removed.
  This shows the test can catch a leak.
- The production read prints only `name|value` lines.
- Runbook 01 points to the tool. The pull request is merged.
