# 2. env-set.sh and the rotation procedure

1. **`bin/env-set.sh <file> <KEY>`** sets one key in one env file on a
   MuMate host.
   - The new value comes from stdin or from `--generate-hex N`, never from
     the command line.
   - Copies the file to a timestamped backup with mode 600 first.
   - Replaces or appends only that key. Every other line stays byte for byte.
   - Prints the key name, whether it was added or replaced, the backup's
     name, and the value's length. It never prints the value.
   - `--help` follows the same shape as `prod-sql.sh`.
2. **Test** `scripts/env-set.test.sh` plants canary old and new values. Both
   must never appear in the output. The test also checks that other lines
   are unchanged, the backup is made, and the file mode is kept.
3. **Rotation procedure** in runbook 01 for the production database password:
   - the owner resets it in Supabase;
   - `env-set.sh` updates `env/fe.env` `DATABASE_URL` and `env/bazi.env`
     `APP_DATABASE_URL`, and `env/backup.env` if it shares the credential;
     slice 1's tool settles that question by hash, without printing the value;
   - recreate fe and bazi, then `bin/ops-status.sh`;
   - a `prod-sql.sh` read proves the new connection.
4. **Proof on staging (mumate-2):** set one harmless key with the tool, then
   check the backup, the single-key diff by key name, and the clean output.

## Acceptance

- `scripts/env-set.test.sh` passes, and fails when value printing is
  forced on. This shows the test can catch a leak.
- The staging run shows the backup and a one-key change, and prints no value.
- Runbook 01 holds the rotation procedure. The pull request is merged.
